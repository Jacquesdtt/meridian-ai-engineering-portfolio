1 · The pitch · 3 min

Explain it in 30 seconds, then in 2 minutes

“Meridian Savings was losing money to silent churn: customers drain their savings account to zero and stop using it. I built a system that ranks every customer by how likely they are to do that next month, using XGBoost. The top 5% go into a review queue, and Azure OpenAI drafts a retention email for each one.

The GenAI part is fenced in. Personal data is stripped out before the model sees anything. Code, not the prompt, caps the interest rate at 3.5%. A human must approve every draft, and approving doesn't send anything. I also built a RAG chatbot that answers questions about the method, using only the final report as its source. I designed all of it around Microsoft's six Responsible AI principles.”

The 2-minute version: five beats

  1. Pin down the problem. The brief left “churn” undefined on purpose. I agreed a precise label with the Head of Data Science: next month the balance rounds to $0 and there is no real activity.
  2. Build a fair test. I turned 6.4M raw transactions into one row per customer per month (2.26M rows). I split the data by time, training on the past and testing on the future, so the model can't cheat by seeing the future.
  3. Beat a real baseline, not accuracy. XGBoost beat a sensible rule-of-thumb baseline on PR-AUC (0.219 vs 0.151) and ROC-AUC (0.723 vs 0.551). Accuracy is misleading here: predicting “nobody churns” scores about 87%.
  4. Choose who to contact based on capacity. A max-F1 cut-off would have flagged about 249k customer-months for review. Setting the cut-off at the top 5% of scores reduced false positives to about 20k without changing how well the model ranks.
  5. Add GenAI with guardrails and a human gate. The system writes drafts only: PII is scrubbed, the rate is capped by Pydantic, there's no /send route, and every approval requires an attention acknowledgement and is written to an audit trail. A RAG bot answers methodology questions.

2 · The problem · 2 min

A bank losing savings deposits without noticing

Counting raw transaction rows makes every month at this bank look active. Why?

The bank pads quiet months with $0 “placeholder” transactions — 523,679 of 6,421,943 raw transactions, or 8.15%. Activity is therefore measured using only non-zero transactions (Monthly_Active_Txn_Count).

Meridian Savings is a US retail bank. Its savings account only pays interest in months where deposits beat withdrawals. The bank uses those deposits as funding, so when balances quietly drain away, the bank loses liquidity. The historical assets under management (AUM) at risk came to about $7.3M.

Sam · Head of Data Science

  • Agree an exact churn definition
  • A sound, auditable model he can own
  • MLflow runs and SHAP for review

Morgan · Product Manager

  • Who to contact, and how many
  • Money at risk, in business terms
  • High / Medium / Low risk language

Jamie · Risk & Compliance

  • Proof the model is fair
  • No autonomous AI contacting customers
  • An audit trail of every decision

The trap: the bank pads quiet months with $0 “placeholder” transactions, so counting raw transaction rows makes every month look active. I measured activity using only non-zero transactions (Monthly_Active_Txn_Count).

The churn label (ADR 004)

Features stop at month t and the label lives in month t+1, so the model can never see the month it is predicting.

To predict next month, the model may only look at this month and earlier. If a feature secretly contained next month's information, the model would look brilliant in testing and be useless in real life. That is called data leakage.

Why one month and not two? Sam wanted enough lead time for the retention team to act. Also, most exit streaks last only one month, and a two-month rule drops the positive rate to about 2.6%.

3 · Architecture · 1 min

The whole system on one page

At serving time, which component talks to MLflow?

None of them. MLflow's database isn't in git, so serving never talks to MLflow: training exports three files to Models/ops/ — the XGBoost booster, the fitted one-hot encoder and serving_meta.json — and the online half loads that folder at startup.

The system splits in two: an offline half trains the model and freezes it into a folder, and an online half loads that folder to score customers, draft emails and run the review queue, calling Azure only for the GenAI parts. Solid boxes are built and tested; dashed boxes are fallbacks or scaffolding.

Reading the diagram

  • Frozen model folder. MLflow's database isn't in git, so serving never talks to MLflow. Instead I export three files to Models/ops/: the XGBoost booster, the fitted one-hot encoder, and serving_meta.json (threshold, run ID, feature names, top SHAP drivers). The server refuses to start if the booster's feature count doesn't match the metadata (ADR 005).
  • Streamlit calls FastAPI for everything. Every score, draft, decision, audit read and RAG question goes through one small client over HTTP, so FastAPI is the single enforcement point and the only writer to SQLite (F8, the Sep 2026 follow-on to ADR 006). Where AppLocker blocks localhost traffic, FRICTION_GATE_MODE=inprocess runs the same FastAPI app through an in-process test client instead of a socket, so no rule is duplicated. API tests use in-memory httpx.ASGITransport.
  • SQLite in WAL mode, single replica. Two writers on a network file share can corrupt SQLite, so Docker Compose and the Container Apps manifest both pin one replica (ADR 008). Postgres is the documented next step for scale.
  • Azure is optional at runtime. Without an endpoint configured, the system uses a deterministic stub drafter and BM25 keyword search, so demos and tests never depend on the network.
4 · The predictive model · 4 min

Classic ML does the deciding, not the LLM

Accuracy on this dataset would be about 87%. Why is that a reason to ignore it?

Because ~87% is what you score by predicting “nobody churns”, catching zero churners — only about 12% of rows are positive. PR-AUC is the honest metric here, and on the test window XGBoost scores 0.219 against 0.151 for the gone_this_month rule.

The LLM never decides who is at risk. A normal machine-learning model (XGBoost) produces a score from numbers, and the LLM only turns that into polite words. That split is deliberate: tabular prediction is a job for gradient-boosted trees, and a regulator can audit a tree model with SHAP.

Features: 24 columns in, 80 model inputs

Each row is one customer in one month. The 24 raw columns include balance and rounded balance, deposit and withdrawal totals, share of flow that is deposits, month-over-month balance change, activity lags (1–3 months back), 3-month rolling means, consecutive inactive months, account age, customer age and state. One-hot encoding the 55 state values (fitted on the training months only) turns them into 80 inputs.

Two leak checks. First, every rolling or lag feature stops at month t. Second, I ran an empirical screen: fit a quick Random Forest, and if any single feature took more than ~50% of the importance, treat it as a likely leak. The top feature (Running_Balance_Rounded) scored 0.273, so it passed.

Split by time, never shuffle

Training stops at 2016-08 and the test window runs 2017-09 → 2020-04, so every test row sits in the model's future; the threshold is chosen on validation only, then frozen for test.

This is one time-based split, not time-series cross-validation with multiple folds. Don't say “CV folds”.

Why XGBoost, and how it was trained

Why this algorithm

  • Handles missing values natively: early accounts have no 3-month lag, so I didn't have to invent numbers
  • Tolerates extreme balance outliers (±1e10) without scaling
  • Works with SHAP for explanations Risk can read

Training recipe

  • binary:logistic, max_depth 6, learning rate 0.08, subsample 0.8
  • Up to 400 trees, early stopping after 40 rounds; best iteration was 99
  • scale_pos_weight = negatives ÷ positives, to handle the 1-in-9 imbalance
  • Fixed hyperparameters, not a search

How good is it? Compare against a real baseline

XGBoost's 0.219 PR-AUC beats both the gone_this_month rule (0.151) and the always-negative floor (0.132); ROC-AUC tells the same story, 0.723 vs 0.551.

PR-AUC asks: “Of the people I flag, how many really churn, across every possible cut-off?” With only 12% positives, that's the honest metric. Accuracy would reward flagging nobody (~87% accurate, zero churners caught). The gone_this_month rule (“they look gone right now”) is a tough, realistic baseline because it mirrors the label.
The PRD's aspirational ROC-AUC > 0.85 was not reached. The definition of done that shipped was “beat the heuristic on PR-AUC and ROC-AUC, and produce a reviewable queue”.

The capacity dial: who actually gets contacted

Moving the cut-off from max-F1 (0.475) to the top 5% (0.701) drops false positives from 248,778 to 20,127 on the same model and the same scores; precision went from 21.1% to 22.9%, and recall from 99.97% to 9.0%.

“I separated two questions. First, does the model rank customers better than a realistic baseline? Yes, on a time-based holdout. Second, who should actually be contacted? On validation data only, I tried to maximise recall with a 40% precision floor and a 5% contact cap. The floor was impossible: even the top 1% was only about 24% precise. So instead of faking it, I documented that and set the threshold by team capacity, at the top 5% of scores. That cut false positives from 249k to 20k without changing ranking quality.”

Scores are ranks, not calibrated probabilities. scale_pos_weight pushes scores upward, so 0.70 means “top of the portfolio”, not “70% chance of churn”. No Brier score or calibration was shipped. Isotonic calibration is future work.

Explainability with SHAP

SHAP splits a prediction into how much each feature pushed the score up or down. Globally (mean |SHAP| on a test sample) the top drivers are Running_Balance_Rounded (3.00), Running_Balance (0.64), then deposits, the 3-month balance mean and withdrawals (≈0.02 each). Demographics are not primary drivers. The report also has per-customer waterfall plots for a high-risk and a low-risk customer.

I attempted dtreeviz, but it failed on the lag-3 NaNs and was skipped, so SHAP is the only explainer that ran. The email drafter receives the frozen global top-5 SHAP driver names from serving_meta.json, not a per-customer explanation.

MLOps: tracking and provenance

MLflow tracked the runs with a SQLite backend (ADR 009): the default file store created thousands of tiny files that corporate antivirus scanning slowed to a crawl. Each run logs parameters, the split, metrics against the baseline, the threshold rule, and the SHAP, Fairlearn and Evidently reports. The served run is 3f575754…, and its ID is returned by /score, shown in /health, and stored on every draft, so any email draft traces back to the training run behind it.

Nothing is registered in the MLflow Model Registry (no aliases or stages), and only the booster was logged, not the encoder. Registering meridian-churn with a champion alias is the documented next step.
5 · The GenAI layer · 4 min

Two GenAI features, both on a short leash

The prompt tells the model never to promise a rate above 3.5%. Suppose it does anyway — what happens?

The prompt is never the enforcement point. After the call, the subject and body are scrubbed again, the rate is clamped with min(rate, MAX_RATE), and the result must pass a Pydantic model whose rate field must be 0 ≤ r ≤ 0.035. That same model re-validates human edits, so an agent can't type 5% either.

Azure OpenAI is used for exactly two things: drafting retention emails (src/genai/drafter.py) and a methodology Q&A bot using RAG (src/genai/rag_engine.py). Both call models deployed in a Microsoft Foundry resource through its OpenAI-compatible /openai/v1 endpoint.

A. Retention email drafts: the full request path

Every guardrail — server re-scoring, the 0.701 gate, PII scrubbing, the rate clamp and the human decision — sits in the request path, where a UI can't skip it, not just in the prompt.

The prompt is a versioned file (prompt-as-code)

src/genai/prompts/retention_draft.prompty is Microsoft's Prompty format: YAML front matter (model settings, typed inputs, a sample) plus a system and user template. The code calls prompty.load and prompty.prepare to render the chat messages. If rendering fails, it falls back to an embedded copy of the prompt, so drafts still work.

model:
  api: chat
  parameters: { max_tokens: 800, temperature: 0.2, response_format: { type: json_object } }
---
system:
You are a Meridian Savings retention drafting assistant.
Never promise rates above {{max_interest_rate}}. Never invent PII or personal names.
Output JSON only with keys subject, body, offered_interest_rate, drivers.

user:
Draft a short retention email for human review only (do not imply the message was sent).
Drivers: {{drivers}}  ·  Churn probability: {{churn_probability}}
Context (already scrubbed aggregates only): {{context_json}}

Don't trust the model's output: validate it in code

def sanitize_llm_draft(data, *, fallback_drivers):
    rate = float(data.get("offered_interest_rate", MAX_RATE))
    return RetentionDraftBody(                       # Pydantic model: rate must be 0 ≤ r ≤ 0.035
        subject=scrub_text(str(data.get("subject", "Retention offer")))[:120],
        body=scrub_text(str(data.get("body", "")))[:4000],   # scrub OUTPUT too
        offered_interest_rate=min(rate, MAX_RATE),            # clamp to 3.5%
        drivers=list(fallback_drivers)[:5],                   # ignore LLM's drivers; use server's
    )

The same Pydantic model re-validates on human edits (PATCH), so an agent can't type 5% either.

What the LLM receives

  • The frozen top-5 SHAP driver names
  • The churn score (rounded)
  • Three safe aggregates: rounded balance, gone_this_month, Is_Inactive_Month
  • The 3.5% cap

What it never receives

  • Customer ID, name, email, phone, DOB, SSN or account number: those keys are dropped
  • Emails, phone numbers, SSN-like and date-like strings, and 8+ digit IDs are regex-redacted
  • The reviewer's identity: review_key is an opaque ID that rejects anything email-like

B. Methodology Q&A bot (RAG)

The bot answers only from the top 3 chunks of the final report: the system prompt says to answer strictly from that context, or reply “I cannot answer this based on the available documentation.”

RAG (retrieval-augmented generation) means: before asking the LLM a question, find the most relevant passages from your own documents and paste them into the prompt with the instruction “answer only from this”. The model answers from your facts instead of its memory, which reduces hallucination.

Decisions worth talking about

  • No vector database. Chroma and FAISS need native DLLs that AppLocker blocked. With one report as the corpus, BM25 and cosine similarity over a few dozen chunks in pure Python are fast enough and easy to unit-test (ADR 010, ADR 015).
  • Chunk size is a quality lever. My first version split only on top-level headings, so some “chunks” were whole ~6,000-character chapters, and three of them looked like the entire report. Splitting on every heading level and packing paragraphs to ≤1,200 characters fixed it. A schema_version in the cache forces a rebuild when the chunker changes.
  • Cache the embeddings. Re-embedding the report on every app restart burned the shared tokens-per-minute quota and caused 429 errors.
  • Resilience (ADR 013). Chat and embedding calls retry with exponential backoff (1–20 s, up to 5 attempts) on 429, timeout, connection and 5xx errors, using tenacity. A 401 on key 1 retries with key 2. Every call logs prompt, completion and total tokens for cost visibility.
RAG is used only for the methodology bot. The email drafter is not RAG-grounded. Since ADR 015 (Sep 2026) retrieval is hybrid (BM25 + embeddings fused with Reciprocal Rank Fusion) with an LLM rerank, but there are no citation IDs and no groundedness evaluation yet. The production path is Azure AI Search with a purpose-built reranker plus groundedness evaluation.
6 · Governance & engineering · 4 min

“Friction as a feature”: making the human step real

What does the API demand before it accepts an approval, and what can the reviewer do afterwards?

Approving requires attention_ack=true, or the API returns 422. Afterwards, nothing: approved or rejected drafts can't be edited or re-opened, the only states are pending_review, approved and rejected, and there is no sent state.

Risk's biggest fear was an AI emailing customers promises the bank never approved. So the architecture makes autonomy impossible rather than merely discouraged (ADR 003). It also works against rubber-stamping, where reviewers click Approve out of habit.

Hard controls (enforced by the API)

  • Drafts start as pending_review. The only other states are approved and rejected. There is no sent state.
  • Approving requires attention_ack=true, or the API returns 422
  • Decide once: approved or rejected drafts can't be edited or re-opened
  • A soft cap of 500 pending drafts returns 429, a capacity discipline
  • Each draft write and its audit row commit in one transaction

Soft nudges (UI)

  • A “read carefully” banner when the score is well above the cut: ≥ max(t + 0.10, 0.80)
  • A warning if Approve is clicked within 8 seconds of opening. It warns only, so people don't learn to click around it.
  • Approve events log attention_ack, high_stakes and seconds open, for Compliance sampling

Role-based access (demo “Glass-Box” RBAC, ADR 007)

The Streamlit role picker and the FastAPI X-Demo-Role header use the same permission matrix from src/serving/rbac.py, so the UI and API can't disagree.

Fairness: measured, disclosed and constrained, but not “solved”

I used Fairlearn's Equalized Odds difference: the largest gap between groups in true-positive or false-positive rate. I measured it on a 100,000-row test sample at the real 0.701 cut, because that's the policy customers actually experience.

SliceGroups kept (n ≥ 500)Equalized Odds diff
Age (6 bands)6 of 6≈ 0.156
State38 of 55≈ 0.318

A first unfiltered run showed a state value of 1.0. That was an artifact of tiny states and near-100% recall at the max-F1 cut, so I added a minimum group size instead of reporting noise. Risk agreed that periodic review plus disclosure is right for now, rather than an automatic release gate (ADR 012).

The residual gaps are real. At the ops cut, the 65+ band has a much higher selection rate (~14.6%) than most bands (~4.6–4.9%). Whether that reflects true churn prevalence or model bias is open future work. Say “disclosed and monitored”, never “fair”.

How harm is limited anyway: the intervention is a positive retention offer, not a denial of service; the top-5% cap limits volume for every group; SHAP shows behaviour (balance, flows), not demographics, driving scores; a human approves every draft; and the gaps appear on the model card.

How I worked with AI coding assistants

I used AI pair-programmers (Antigravity for heavy generation, Cursor for review) and treated managing them as an engineering discipline:

  • Rules as a single source of truth. AGENTS.md holds the project constraints (no leakage, AppLocker-safe commands, ADR triggers). .cursorrules is compiled from it.
  • Docs before code. When something was challenged, I wrote an attack note and a signed-off revision plan before touching src/. When I once skipped that step, I backfilled it and tightened the rule.
  • A human runs the notebooks. The agent edits cells, I run them, and saved outputs are the source of truth, not the agent's side scripts.
  • An anti-speculation rule. Nothing gets documented as deployed unless it is. That is why the Container Apps and Foundry-agent work is clearly marked as open.

9 · Interview Q&A · 6 min

Likely questions, with answers you can defend

Tap a question to open it. Practise the first sentence of each answer out loud: it's the headline.

Why XGBoost and not an LLM or a neural network?

It's tabular, numeric panel data, which is where gradient-boosted trees are strongest. XGBoost handles missing lag values and extreme balances natively, trains in minutes, and works with SHAP, so Risk can audit it. An LLM would be slower, costlier, non-deterministic and far harder to explain for a yes/no risk score. I used the LLM where language is the product: writing the email.

How did you prevent data leakage?

Three layers. Design: features stop at month t and the label is month t+1. Evaluation: I split by time (train 2007–2016, validate 2016–17, test 2017–2020) and chose the threshold on validation only. Empirical check: a quick Random Forest leak screen flags any feature with more than ~50% importance; the top one was 0.273. I also excluded customer IDs and raw month strings so the model can't memorise.

Why PR-AUC instead of accuracy or ROC-AUC?

Only ~12% of rows are churn, so accuracy rewards predicting nobody churns (~87%). ROC-AUC is built on the false-positive rate, which stays flatteringly small when negatives vastly outnumber positives. PR-AUC focuses on precision among flagged customers, which is what a retention team pays for. I reported both and required both to beat a real baseline: 0.219 vs 0.151 PR-AUC, and 0.723 vs 0.551 ROC-AUC.

How did you choose the cut-off?

I separated ranking quality from contact policy. Max-F1 gave a threshold of 0.475, which flagged most of the test table: 249k false positives. On validation I tried to meet a 40% precision floor within a 5% contact cap, but precision plateaus around 23–24% even at the top 1%, so the floor was infeasible. I documented that and used the top-5% validation quantile (0.701), which cut false positives to 20k with the same ranking metrics. Lowering it to chase recall only makes sense if review capacity grows.

How do you stop the LLM promising a bad interest rate or leaking data?

I never rely on the prompt alone. Before the call, the server re-scores the customer and refuses unless they're above the cut. Blocked fields are dropped and PII patterns are redacted, and the model only sees driver names, a score and three aggregates. After the call, the subject and body are scrubbed again, the rate is clamped to 3.5%, and the result must pass a Pydantic model whose rate field is capped at 0.035. That same model re-validates human edits. The draft is stored as pending review, and there's no send endpoint at all.

Explain your RAG bot. Why no vector database?

It answers methodology questions from the final report. I chunk the markdown by headings into pieces of at most 1,200 characters, embed them with text-embedding-3-large, and cache the vectors on disk. For each question I rank chunks two ways, BM25 keyword scoring and embedding cosine similarity, fuse the two rankings with Reciprocal Rank Fusion, let the chat model rerank the shortlist, and pass the top 3 to the chat deployment with an instruction to answer only from that context or say it can't. There's no vector DB because the corpus is one report and AppLocker blocked the native libraries. At scale I'd move to Azure AI Search and a purpose-built reranker instead of the LLM rerank. One lesson: chunk size matters. My first chunks were whole chapters, so “top 3” was basically the entire report.

What happens when Azure OpenAI is throttled or down?

Transient errors (429, timeouts, connection errors, 5xx) retry with exponential backoff, up to 5 attempts, using Tenacity. A 401 on the primary key retries with the secondary key. If it still fails, the drafter returns a deterministic compliant stub marked stub_fallback, so the review queue keeps working and Compliance can see what happened. The RAG bot returns a safe message instead of crashing. Token usage is logged on every successful call.

Walk me through Responsible AI in your project.

Fairness: Equalized Odds by age and state at the live threshold, disclosed. Reliability: out-of-time testing, fallbacks, retries, 127 tests. Privacy: PII scrubbed before and after the model. Inclusiveness: plain-language, role-specific views. Transparency: SHAP, a glass-box page and a model card. Accountability: a human approves every draft, with an audit trail and recorded decisions. Then name one gap, such as demo roles instead of Entra ID.

Your fairness numbers show gaps. Is the model biased?

I can't claim it isn't. At the live cut, the Equalized Odds difference is about 0.16 by age and 0.32 by state, and the 65+ band is selected more often. What I can show: I measured at the threshold customers actually experience, filtered out tiny groups that produced a fake 1.0, and confirmed through SHAP that behaviour drives the scores. The intervention is a retention offer, not a denial, volume is capped, and a human reviews each case. Risk agreed on disclosure plus periodic review. The next step is to test whether the age skew reflects real churn prevalence and to agree a numeric fairness gate with Risk.

How would you take this to production on Azure?
  • Identity: Entra ID sign-in with app roles replacing demo roles; managed identity for calls to Foundry; secrets in Key Vault
  • Hosting: Container Apps with a managed database (e.g. Azure Database for PostgreSQL) instead of SQLite, so the API can scale past one replica
  • GenAI: Foundry SDK project endpoint, the Responses API, custom guardrails, the temperature fix, and evaluations for groundedness and relevance
  • RAG: Azure AI Search, hybrid retrieval with reranking
  • MLOps: register the model with a champion alias, log the full pipeline, calibrate scores, schedule drift monitoring, and add tracing
Tell me about a mistake or a hard lesson.

A good one is a silent failure. prompty 2.x couldn't render my prompt file, and because I'd built a graceful fallback, the drafter quietly used the embedded prompt instead. Nothing crashed. I only caught it when a test failed during a clean re-install. I pinned prompty<2. The lesson: every fallback needs a test or a signal, otherwise resilience hides regressions. Backup story: my first threshold (max-F1) looked statistically great but would have flooded reviewers with 249k false positives.

How did you handle stakeholders?

The churn definition wasn't in the brief, so I prepared options with data (one- vs two-month rules, rounding, grace period) and agreed it with Sam, then recorded it in ADR 004. I ran two red-team rounds on the serving layer from Jamie's Risk perspective, and they produced concrete changes: a required role header, immutable decisions, an approval acknowledgement and frozen LLM drivers. For Morgan, I translated scores into capacity and at-risk AUM. Each stakeholder's concern maps to a control in the code.

Why does this matter for a Microsoft-focused consultancy?

Client environments look like mine did: locked-down laptops, security policies and compliance stakeholders who say no. I delivered inside those constraints, recorded every trade-off in an ADR, used Azure OpenAI through Foundry, applied Microsoft's Responsible AI principles as code, and kept the documentation honest about what was and wasn't deployed. That's the difference between a demo and something a regulated client can trust.

Glossary in plain English

Churn (here)
Next month the balance rounds to $0 and there are no real transactions.
Data leakage
Future information sneaking into training, which makes test scores look better than real life.
PR-AUC
How precise your flags are across all cut-offs; the right lens when positives are rare.
ROC-AUC
The chance the model ranks a random churner above a random non-churner.
Threshold / cut-off
The score above which a customer enters the review queue; here set by capacity.
SHAP
Splits one prediction into each feature's push up or down, based on game theory.
Equalized Odds diff.
The largest gap between groups in true-positive or false-positive rate. 0 means equal.
Calibration
Whether a score of 0.7 really means 70% of such customers churn. Not done here.
MLflow
Records each training run's settings, metrics and files so results are reproducible.
RAG
Retrieve your own relevant text first, then ask the LLM to answer from it.
Embedding
A list of numbers representing meaning; similar texts get similar vectors.
Cosine similarity
How closely two vectors point the same way; used to rank chunks.
TF-IDF
Keyword scoring that favours words that are frequent in a chunk but rare overall. The original offline fallback, replaced by BM25 in ADR 015.
Prompty
Microsoft's file format for prompts: settings, inputs and system/user templates, versioned like code.
Deployment (Foundry)
A named instance of a model in your resource. Code calls the deployment name.
HITL
Human in the loop: a person must approve before anything consequential happens.
Pydantic
Python validation that rejects data outside defined types and limits.
RBAC
Role-based access control: what each role is allowed to do.
ADR
Architecture Decision Record: a short note of a decision, alternatives and trade-offs.
SQLite WAL
A journal mode that lets readers and a writer work at the same time with fewer locks.
429
HTTP “too many requests”: you hit the rate or token quota, so back off and retry.
AppLocker
Windows policy that blocks unapproved executables; it shaped many decisions here.

PR-AUC on the test window: the model versus the baseline rule?

0.219 for XGBoost versus 0.151 for the gone_this_month rule. Always predicting “no churn” scores 0.132.

0.70055 — the top 5% of validation scores, a capacity cut sized to what the team can review. Scores are uncalibrated risk ranks, so 0.70 means “top of the portfolio”, not “70% chance of churn”.

How many false positives at the max-F1 cut, and how many at the shipped cut?

248,778 false positives at the max-F1 threshold of 0.475, down to 20,127 at the top-5% threshold of 0.701 — with no change in ranking quality.

Fit 2007-03 → 2016-08 (114 months, 1,568,631 rows), validation 2016-09 → 2017-08 (12 months), test 2017-09 → 2020-04 (32 months). One chronological split, not CV folds.

3.5% (0.035). Code, not the prompt: the rate is clamped with min(rate, MAX_RATE) and a Pydantic model requires 0 ≤ r ≤ 0.035. The same model re-validates human edits.

About $7.3M of historical assets under management (≈ $7.27M).

A quick Random Forest importance screen: any single feature taking more than ~50% of the importance is treated as a likely leak. The top feature, Running_Balance_Rounded, scored 0.273, so it passed.

Approving requires attention_ack=true or the API returns 422; and approved is not sent, because no /send route and no sent state exist. Also: decisions are final, and a soft cap of 500 pending drafts returns 429.
